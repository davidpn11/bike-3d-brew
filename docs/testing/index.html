Testing

Three layers, cheapest first. CI (.github/workflows/ci.yml) runs all of them on every PR.

LayerWhereRuns inCommand
Unitapps/web/test/*.test.tsVitest, Node (happy-dom per file where needed)npm test
Coveragesame tests, V8 coverageVitestnpm run test:coverage
End-to-endapps/web/e2e/*.spec.tsPlaywright, Chromium + SwiftShader WebGLnpm run e2e

Fixtures for both come from one generator: tools/fixtures/make-capture-bundle.mjs.

Unit tests

  • Pure logic lives in apps/web/src/scene/ (scene format, store, camera math, capture bundles, UI helpers in helpers.ts) and is tested in plain Node. When UI code grows a decision (a default, a message, a URL rule), move it into src/scene/helpers.ts and test it there.
  • three.js code that needs no WebGL (loaders, centerOnGround, the demo bike's geometry) is tested in Node too (viewer-node.test.ts). three's FileLoader needs a ProgressEvent stub in Node; the test file installs one. Models are passed as data: URLs.
  • DOM code (ui/dom.ts, viewer/pins.ts, ui/photoViewer.ts, ui/photoLibrary.ts, ui/photoDecode.ts) opts into happy-dom with a first-line comment // @vitest-environment happy-dom. Browser APIs happy-dom lacks are stubbed per test: createImageBitmap, <img>.decode, OffscreenCanvas, Worker (photoDecode), pointer capture (lightbox gestures), a fake Viewer (pins). Decoding itself is mocked in photoLibrary.test.ts.
  • Storage: storage/backends.ts runs against fake-indexeddb and a small in-memory OPFS (FakeDir in backends.test.ts); navigator is replaced with vi.stubGlobal.
  • Zip parsing: zipIndex.test.ts hand-builds zips byte by byte (zip64 records and extra fields, foreign extras, odd methods, lying sizes), branches fflate never writes.
  • USD: usdz.test.ts loads the committed binary USDC fixtures (apps/web/test/fixtures/, made by tools/fixtures/make-usdc.py with Pixar USD); usd-units.test.ts drives the crate decoders and composer fast paths directly for encodings the fixtures do not contain.

Coverage

npm run test:coverage writes coverage/ (text summary, HTML report, coverage-summary.json). Thresholds in apps/web/vite.config.ts are a ratchet set just under the current numbers, globally and for src/scene/**; CI fails when coverage drops below them (and the web job prints the totals in its step summary). At the time of writing: lines 99.8%, statements 98.9%, functions 98%, branches 92.8%. When you raise coverage, raise the thresholds in the same PR. Never lower them to make a PR pass.

make-capture-bundle.mjs

buildFixtures() returns every fixture as bytes and is also imported by unit tests. Output is byte-for-byte deterministic (fixed zip timestamps, rounded floats), so nothing binary is committed. What it makes:

FileWhat it exercises
bike.bikecapture.zipiOS layout (everything under one folder): manifest, ASCII-USD model.usdz of a low-poly vertex-colored bike (wheels, frame tubes, fork, cockpit, saddle, drivetrain as named meshes), poses.json with 32 cameras on three rings looking at the bike, 32 tiny placeholder PNG photos, record.json
bike-glb.bikecapture.zipsame bike as GLB (three's GLTFExporter in Node, vertex colors)
bike-flat.bikecapture.zipflat zip with Finder __MACOSX junk

The photos are PNG stand-ins: real captures have HEIC, which Node cannot encode.

Rendered-photo bundle

The E2E global setup (apps/web/e2e/global-setup.ts) also renders the make-capture.mjs bike from each of its poses with render-photos.mjs (headless Chromium, three.js, the iPhone wide camera's field of view) and writes bike-photos.bikecapture.zip, so photo close-ups are ranked and shown from real images of the fixture.

End-to-end tests

Playwright drives the production build (vite build + vite preview on port 4190, started by the config's webServer) in two projects: desktop (1280×800, every spec) and mobile (iPhone 14 viewport with touch, DPR 1 to keep CPU rendering fast; only the specs where layout and touch matter: view, edit, present, photos). WebGL runs on SwiftShader (--use-angle=swiftshader --enable-unsafe-swiftshader), so no GPU is needed. CI splits the suite into two parallel shards (--shard=1/2, 2/2).

Browser: CI runs npx playwright install --with-deps --only-shell chromium. On a machine with a preinstalled Chromium (e.g. the agent containers: /opt/pw-browsers/chromium), do not run playwright install; set PW_CHROMIUM_PATH=/opt/pw-browsers/chromium and the config uses it as launchOptions.executablePath. @playwright/test is pinned to the version whose browsers are preinstalled there.

The window.__bike test hook

main.ts exposes window.__bike = { app, store, viewer, ready } only in the dev server or when the URL has ?e2e (the suite always adds it). Tests use it to:

  • wait for state instead of sleeping: ready (boot finished), a model in viewer.modelRoot, viewer.flying (camera animation running);
  • find a point on the model to tap: modelPoint() in e2e/helpers.ts asks the app's own viewer.pick() and checks document.elementFromPoint so the tap lands on the canvas, not a pin;
  • read the scene for assertions (store.scene).

Everything else goes through the real UI: clicks, taps, keys, the file picker (setInputFiles), real DragEvent drops with a DataTransfer, dialogs and downloads. Keep the hook read-mostly; if a test needs to mutate app state through it, that is a sign a UI path is missing.

Writing reliable E2E tests

  • Never waitForTimeout. Wait on app state (waitForFunction, expect.poll) or on web-first assertions (toHaveText, toHaveCount, toHaveAttribute).
  • Camera flights are instant because the suite emulates prefers-reduced-motion: reduce, which the viewer honors; a test that wants the animation calls page.emulateMedia({ reducedMotion: 'no-preference' }) and waits for viewer.flying === false.
  • Use collectErrors(page) and assert it is empty where a flow should be clean.
  • Screenshots are for humans: snap(page, testInfo, name) saves to test-results/ and attaches to the HTML report. Do not add pixel-diff assertions; SwiftShader output differs across machines.
  • Tests run in parallel across fresh browser contexts, so each test starts from an empty localStorage and the seeded demo.
  • On CI a failing run uploads playwright-report/ and test-results/ (traces, screenshots) as the playwright-report artifact. CI retries once; a test that only passes on retry is reported as flaky and should be fixed, not ignored.

What the suite covers

  • view.spec.ts: demo loads with seeded areas/comments/pins and no console errors; fly to an area and back; comment focus; background modes (and the chroma-green opaque clear); Snapshot downloads a real PNG; Reset view.
  • edit.spec.ts: add/edit/delete a comment picked on the canvas; persistence across reload; Cancel/Escape; default area; save/rename/set view/delete areas; bike details.
  • present.spec.ts: keys (←, →, space, Esc) and ‹ › buttons with wrap-around; ?mode=present.
  • files.spec.ts: export JSON → re-import; ?scene= published scene (routed); capture bundles via picker and drag-and-drop (USDZ, GLB, flat); re-drop after reload restores comments; broken poses warning; bare model drop; error toasts for seven kinds of bad files.
  • storage.spec.ts: everything still works with localStorage throwing.
  • capture-cache.spec.ts: a reload reopens the last capture from OPFS with its comments; the Open menu lists stored captures (most recent first, size, current one marked), switches between them, closes on Esc / outside click, "Choose a file…", forgets them; forgotten means a reload asks for the zip again. files.spec.ts keeps the re-drop flow with capture storage blocked (blockCaptureStorage()).
  • photos.spec.ts: a saved area shows its best photos (all thumbnails decode), the lightbox steps with ←/→ and ‹ › with wrap-around, Esc closes only the lightbox; Present mode shows the strip; after a reload the thumbnails come from browser storage.
  • files.spec.ts also drops the committed binary USDC fixture and checks it renders with its diffuse and normal textures decoded.
