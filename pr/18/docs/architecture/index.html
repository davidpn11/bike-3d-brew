Architecture

Why Object Capture instead of Wes Bos' room pipeline

wesbos/3d-model-anything records RoomPlan + LiDAR mesh + posed photos, then an AI agent rebuilds the room in three.js. A bike is one object with thin tubes, spokes and cables, so we use Apple's Object Capture: guided orbits, automatic object masking (the background is removed during reconstruction; no green screen needed) and a textured USDZ. We keep Wes's key idea of posed photos: poses.json tells us where each photo was taken, so the viewer can show real close-up photos for an area (e.g. the fork crown) next to the 3D view.

Fallbacks when Object Capture struggles with a bike (thin spokes are the classic failure): area mode + a crop box, or a gaussian splat (Scaniverse/Polycam/Luma) for photoreal paint. The green background mode exists for compositing snapshots/videos in other tools.

Contracts

bike-capture/1 (iOS export zip)

PathContent
manifest.json{ schema, name, createdAt, device, systemVersion, mode: "object"|"area", model, poses, images, photos?, imageCount }
model.usdzreconstruction, meters, +Y up
poses.json{ schema: "bike-poses/1", samples: [{ sample, file, transform[16] }] } (column-major camera→model)

photos/optional: JPEG copies of images/, same file stems, ≤ 2048 px long edge, EXIF orientation baked into the pixels (orientation 1). Listed as manifest.photos

Importing in the browser (apps/web/src/scene/capture.ts): dropping a *.bikecapture.zip unzips it in memory with fflate; nothing is uploaded. The iOS exporter zips its staging folder (NSFileCoordinator .forUploading), so files usually sit under one top-level directory: the shallowest manifest.json defines the bundle root and __MACOSX/ / ._* entries are ignored. Only manifest.json, the model and poses.json are decompressed (size-capped); images are just listed; when manifest.photos names a non-empty folder, its JPEGs are used instead of the HEICs (pose file names like IMG_0007.HEIC match IMG_0007.jpg by stem), so no browser needs the WASM HEIC decoder. If manifest.model is missing, a glb/gltf/usdz/ply next to the manifest is used (GLB first, e.g. after tools/usdz-to-glb.py). A broken poses.json is a warning, not an error.

The resulting scene gets a stable id (capture-<name>-<createdAt digits>) so dropping the same bundle again restores its saved areas and comments, and a model URL bundle:<zip name>/<path>, which is never fetched: it is resolved from memory or from the capture cache below, and only when neither has it does the viewer ask for that zip to be dropped again.

Capture cache (browser storage)

So a capture scene survives a reload, every successfully opened bundle is kept in the browser (apps/web/src/scene/captureCache.ts, pure logic; apps/web/src/storage/backends.ts, storage):

  • What: the model bytes, manifest.json, poses.json and the image list. Lazily extracted files (photos, thumbnails) can be added to an entry later (putFile) and are evicted with it. The zip itself is not kept (HEIC photos make it hundreds of MB).
  • Where: OPFS (navigator.storage.getDirectory(), folder bike-captures/, flat percent-encoded file names), falling back to IndexedDB (bike-3d-brew / files) when OPFS is missing, has no createWritable() (older Safari) or refuses a probe write. Neither → no cache, the old "drop the zip again" behavior. navigator.storage.persist() is requested once per page load, on the first store.
  • Keys: one entry per bundle: model URL; files live under cap-<slug>-<fnv1a(url)>/… and an index.json lists entries (validated on read). An entry remembers the scene id it was opened as, so a different bike exported with the same zip filename never loads the wrong model.
  • Budget: LRU by last use, min(500 MB, 50% of the quota − other usage) from navigator.storage.estimate(). A bundle larger than the whole budget is simply not cached.
  • Failure: every call is best effort. Any storage error leaves the app as if the cache did not exist; entries whose files vanished (browser eviction) are dropped from the index.
  • UI: "Open…" becomes a small menu once something is stored: "Choose a file…" plus the stored captures (name, size, × to forget).

USDZ loading (apps/web/src/viewer/usd/)

Object Capture writes a USDZ whose root layer is binary USDC (crate): one baked triangle mesh, indexed face-varying primvars:st and normals, a UsdPreviewSurface fed by UsdUVTexture PNGs in 0/ (diffuse, normal with scale 2 / bias -1, occlusion), metersPerUnit = 1, upAxis = "Y".

three.js r186 can read this: USDLoader (the old USDZLoader is a deprecated alias) has a crate parser with LZ4 + integer decoding (usd/USDCParser.js) and a composer that handles xforms, GeomSubsets, indexed/face-varying primvars, UsdPreviewSurface textures, metersPerUnit and Z-up. We reuse those parsers and patch what fails on real-world files:

  • crate.ts (CrateParser): values the crate stores inline that r186 misreads: small integral double2/3/4 and half3/4 (packed int8, e.g. xformOp:translate = (0, 0, 5) became a number and crashed the transform), negative int, half; plus scalar half3/4, quath, int4, matrix2d/3d.
  • composer.ts (FastUSDComposer): typed-array fast path for all-triangle meshes. Stock three took ~1.4–2.2 s to build a 1M-triangle mesh (JS arrays per index); this takes ~0.2 s, same output.
  • usdz.ts (loadUsd): unzips only USD layers and images, takes the first layer as root (falls back to the first USD layer anywhere), composes, welds the face-varying expansion back into an indexed mesh (../weld.ts: 2.9M → 0.49M vertices for 1M triangles), waits for textures (blob URLs created and revoked by three per image), halves three's normal-map strength for the standard scale 2 / bias -1 decode, and reports undecodable textures as warnings instead of failing.

Measured on a synthetic 23 MB USDZ (972k triangles, 2048² texture; tools/fixtures/make-usdc.py --detail 90 --tex 2048), Chromium: unzip 16 ms, parse 183 ms, build 206 ms, textures 24 ms. Parsing stays on the main thread: a worker would save the ~0.2 s parse but pay ~0.07 s structured-clone of the spec table back, and the build step needs three.js objects on the main thread anyway. The USD code (~70 KB min) is a lazy chunk loaded on the first USDZ. Anything that still fails shows an error pointing to tools/usdz-to-glb.py. Fixtures are synthetic (apps/web/test/fixtures/README.md).

Rendering and performance (apps/web/src/viewer/)

Details and measurements: PERFORMANCE.md.

  • Render on demand (renderScheduler.ts): the animation loop only runs while something changes. Viewer methods (setModel, setView, applyTransform, setBackground, resize, controls input, fly-to) call viewer.requestRender(); code that mutates the three.js scene directly must call it too. The shadow map is redrawn only on requestRender() (scene changes), never for camera-only frames. Frame listeners (onFrame, pins) run after drawn frames only.
  • Quality (quality.ts): pixel ratio ≤ 2 (1.5 on phones for captures over 400k triangles), MSAA only at 1×, smaller hard shadows on phones; ?quality=low|high overrides.
  • Raycasts (bvh.ts): after the first frame of a model, meshes over 5k triangles get a three-mesh-bvh hierarchy (built in bvh.worker.ts for big meshes, indirect so the GPU index buffer is untouched). viewer.raycastReady tells the pins when occlusion tests are cheap.
  • Pins (pins.ts): allocation-free projection against a cached viewport size, transform-only writes for pins that moved, offscreen class for pins behind the camera or off the stage, occlusion raycasts under a 3 ms per-frame budget that finish on idle animation frames.
  • GLB decoders (loaders.ts, gltfInfo.ts): extensionsUsed decides which of Meshopt, Draco and KTX2/Basis is imported; their WASM ships in the build (no CDN).

bike-scene/1 (viewer JSON, *.bike.json)

See apps/web/src/scene/schema.ts. A scene references its model by URL (relative to the scene file), lists hotspots (named camera views: the zoomable areas) and annotations (surface point + normal, title, body, kind feature|spec|upgrade|note, optional price and area). All coordinates are in model-root space.

Model transform. The loader wraps the model so its native bounding box is centered on X/Z and rests on y = 0 (centerOnGround, deterministic per file); that frame is model-root space. model.scale, model.rotation (Euler XYZ, three.js convention) and model.offset are then applied to the root as world = offset + R · (scale · p). Annotations and hotspot views stay in model-root space, so re-orienting a capture never detaches a comment. The overview camera is framed in world space (camera up is world +Y) and converted back.

Crop box (crop?: { min, max, enabled }, model-root space, optional and lenient: a malformed crop is dropped, swapped corners are reordered). The viewer turns it into six world clipping planes on the model's own materials (local clipping, shadows clipped too), recomputed only when the model transform or the box changes. Raycasts skip hits outside the box (no comments on cropped-away parts, no occlusion by them), pins outside it are hidden, and exact bounds (framing, on-ground, auto-orient samples) only count kept vertices. Edit mode shows the box with one handle per face (viewer/cropBox.ts): pointer events in the capture phase, so mouse and touch drags never orbit the camera; the face moves along its axis to the point nearest the pointer ray, clipping live, and the store is updated once on release. "Fit to bike" (scene/crop.ts, pure) samples points along triangle edges, cuts above the floor slab (a dense, wide band in the lower third of the up axis) and keeps the largest 26-connected voxel cluster with a 2% margin. Area-mode captures get that box pre-computed but disabled, a hint in the toast, and auto-orient waits until the crop is on. Turning the crop on/off or fitting it re-grounds the visible part.

Auto-orient (apps/web/src/scene/orient.ts, pure, unit-tested). Target frame: +X front, +Y up, +Z drive side, tyres on y = 0. Up to 50k strided vertices (≈3 ms for 1M vertices):

  1. PCA: smallest-variance axis = the bike's width, middle axis = candidate up.
  2. Up sign by votes: the centroid sits below mid-height (wheels), and the top band (handlebar) is wider across than the bottom band (two tyre contact patches).
  3. Ground line: the longest downward-facing edge of the side-view convex hull (tangent across both tyres) fixes the 5–15° tilt PCA leaves.
  4. Object Capture output is gravity-aligned, so if that up is within 6° of ±Y, Y is kept exactly and only yaw changes (horizontal PCA).
  5. Front sign: the wide handlebar sits ahead of centre (plus a small vote for the drivetrain mass behind it). Drive side follows from the right-handed frame.

It runs once when a scene is opened with a non-demo model, no comments and no model.rotation (shouldAutoOrient); the offset is then recomputed from exact bounds so the bike stands on the ground. Edit → Model exposes the result plus manual rotate/flip/scale/nudge, each one store update with a small undo stack. Generate tilted test bundles with node tools/fixtures/make-bike-capture.mjs --rotate 70,25,-40 (ASCII USD mesh in model.usdz).

bike-share/1 (share package, *.bikeshare.zip) and the customer link

Share → "Export share package" turns a local capture into a self-contained zip (apps/web/src/scene/share.ts):

PathContent
bike-share.json{ schema: "bike-share/1", id, name, createdAt, scene, model, photos }
scene.bike.jsonthe bike-scene/1 scene, model URL rewritten to the packaged file
model.glb|usdz|…the 3D model
photos/*.jpgthe close-ups referenced by Hotspot.photos

tools/publish-scene.mjs validates a package (size limits: zip 300 MB, model 250 MB, JSON 2 MB, 8 MB × 64 photos; JPEG only; no paths outside the package; parseScene) and installs it under apps/web/public/scenes/<id>/. The customer link is …/app/?scene=scenes/<id>/scene.bike.json&view=present (kiosk=1&interval=<s>&idle=<s> for a shop screen). Scene, model and photo URLs must be same-origin or https.

src/entry.ts loads only present/BikePresenter.ts for ?view=present, so customers never download editing code. The presenter is a self-contained module: mountPresenter(container, options) returns a controller with goToArea, next, prev, play, pause, setBackground and on(event) for ready, error, areachange and commentopen. It scopes its CSS under .bike-present and only takes keys while focused, which is the base for an iframe embed or a <bike-viewer> element (see ROADMAP).

Photo close-ups

For the active area (its view target, preferring cameras on the side its saved view looks from), the active comment (its pin, preferring cameras in front of its surface normal) and each Present step, the viewer shows a filmstrip of the capture photos that best show that point; tapping one opens a full-screen viewer (arrows / swipe, pinch / wheel / double-tap zoom, Esc).

  • Spaces. A pose is a column-major camera→reconstruction matrix, camera looking down -Z, +Y up. Scene positions are in model-root space. Viewer.setModel adds centerOnGround(object) to the model root, so modelRoot ⟵ reconstruction is the loaded object's local matrix (the centering shift plus any root transform the loader applied) times the identity wrapper: src/viewer/captureSpace.ts. The scene's model.rotation/scale/offset sit on the model root itself and never enter the mapping. A unit test runs the fixture USDZ through three's USDLoader + centerOnGround and checks the expected close-ups win.
  • Ranking (src/scene/photos.ts, pure): keep photos whose frustum contains the target (assumed iPhone wide camera, 65° × 51°, landscape sensor; poses carry no intrinsics), drop cameras behind the surface (side hint), score 0.45·centered + 0.35·closeness + 0.2·facing (closeness relative to the nearest usable photo, so units do not matter), and skip near-duplicate viewpoints. Occlusion is not tested.
  • Photos (src/ui/photoLibrary.ts): extracted one at a time from the dropped zip via its central directory (src/scene/zipIndex.ts: the File stays on disk, nothing else is inflated), decoded natively (createImageBitmap, then <img>; Safari reads HEIC), else HEIC goes to a module worker that lazily loads libheif (libheif-js, WASM, ~2 MB, LGPL-3.0, only fetched when a HEIC photo is shown). Results are downscaled to JPEG (360 px thumbnails, 2048 px full) and added to the capture cache entry, so after a reload the photos already seen still show without the zip.

Open questions (verify on device)

  • Does PhotogrammetrySession.Poses return camera→model transforms in the same frame as the USDZ? (Assumed, and the photo close-ups depend on it; validate by checking that an area's top close-up really shows that area on a real capture.)
  • Does three.js read Object Capture USDZ (binary USDC)? Yes, with the fixes above, verified on synthetic Object-Capture-like files. Still to confirm on a real capture (docs/MANUAL-STEPS.md).
  • Bike size vs. Object Capture's bounding box limits: area mode is the fallback.
